# Isolated agent runtime

The API persists a run before asking the host supervisor to execute it. The supervisor constructs `RuntimeRequest` exclusively from current membership, project access, authorized storage mounts, and a short-lived inference grant. Browser-supplied host paths, tokens, runtime options, images, and container commands must never be forwarded.

`DockerRuntime.execute` journals before dispatch; creates a **private internal network per run**; connects only the application inference gateway; and launches one container for the turn. Containers have a read-only root, UID 10001, no Linux capabilities, no-new-privileges, Docker's default seccomp policy, the required AppArmor profile, private IPC, bounded memory/CPU/PIDs, and no host sockets. Organization sharing is expressed through authorized nested volume mounts. A read-only session forces **every** workspace mount read-only even if the project/share permits writes. `/tmp` is disposable; `/session` is native history isolated to the conversation, outside uploaded files. No upstream or management credentials are mounted. Public internet access requires an explicit per-run proxy capability and an allowed supervisor proxy origin; it is disabled when either is absent. The image also includes a pinned offline React/Vite build toolkit and ordinary Python/Poppler document readers.

The private network is essential: a shared bridge would let agents connect to servers started by other projects. The gateway is the only peer and validates the run token, membership, project, and model on every inference request. When enabled, the same private API peer hosts the authenticated public HTTP/S proxy. The runtime accepts only a credential-free HTTP origin on an explicit nondefault port whose hostname matches the gateway and whose origin is in the supervisor allowlist. It derives proxy authentication inside the runner from the existing project/run grant. Standard curl/Git/Python/npm environments and Node fetch use the proxy, while the inference gateway and container loopback bypass it. The private run bridge still has no direct public route; public-address checks, denied host/container addresses, quotas, and revocation remain enforced by the proxy. No upstream credentials or ambient host environment are inherited by native children. Cancel/revoke a run before revoking a mounted organization share. Revoking future mounts alone cannot revoke an already-running container's mount.

Source paths are not ordinary unchecked Docker binds. Managed storage roots are anchored in local Docker volumes and each authorized source uses `volume-subpath` (Docker 26+). Docker's `safepath` pins the selected inode before mounting and prevents escapes outside the volume. Because Docker permits symlinks to other paths _inside_ that volume, the supervisor also opens each source using a descriptor-anchored, no-follow Linux traversal, retains the descriptor, and sends a target/device/inode/type manifest. Trusted image code verifies that manifest before launching any harness or loading project configuration. A source swapped after authorization causes admission to fail, including swaps to another organization within the same storage root. The managed root and its parents must never be writable by agent containers.

The container receives a single bounded JSON request through stdin, emits ordered NDJSON events, and exits. Native session identities are persisted by the conversation service. Subsequent user turns resume the corresponding native session; there is no published-document-release prerequisite or snapshot binding. Agent code remains real provider execution—there is no canned-response fallback.

The Grok Linux amd64 binary is downloaded from the official distribution URL and pinned by SHA-256 `9ce03ed23e16ea01072b4496263d6213a27899e1e3e107f008d36edf82e70407`. The image currently targets Linux amd64; ARM requires its own verified binary checksum. npm SDK transitives are resolved in the repository lockfile. Native protocol changes require fixture tests and live acceptance before updating pins.

## Recovery and acceptance

Each run ID is single-use. A supervisor restart force-stops any journaled uncertain container and removes its private network before returning interrupted IDs; it never submits the prompt again. The API must recover its durable lease/state using these results and retain completed/partial output. Failure to contact Docker or confirm cleanup blocks recovery. A run is reported terminal only after its container has stopped. Runtime stdout is bounded; native stderr is not sent to users because it may contain secrets or document data.

Load `wme-platform-agent.apparmor` on the Linux host before building/launching containers. The entrypoint fails closed if UID, seccomp, no-new-privileges, capability state, or AppArmor enforcement is missing. Session directory and project volume ownership must be prepared for UID 10001 by the supervisor. Application DB, supervisor token, Docker socket, and upstream credentials must live outside allowed storage roots.

Unit tests use synthetic processes and a fake Docker executable; they do not authenticate accounts or start Docker Desktop. These establish protocol routing, bounds, duplicate suppression, cancellation, recovery and generated isolation arguments. They are **not** proof of Linux kernel isolation or upstream account entitlement. Before production enablement, run Linux container acceptance for read-only/write mounts, cross-project network exclusion, denied control-plane files/sockets, forced cancellation and restart recovery; then test a real account for each selected harness through the central gateway.

`WME_RUN_CONTAINER_ACCEPTANCE=1 bash platform/runtime/check-container.sh` builds the pinned image and runs actual Linux boundaries plus complete native turns and persisted-session resume for all four harnesses. Its deliberately synthetic local gateway implements Responses, Messages, and Chat Completions streams; it is test-only and is never copied into the product image or used as a provider fallback. This verifies protocol/configuration compatibility without authenticating or spending an upstream account. It does not establish live provider acceptance. The same acceptance also builds a React dashboard offline and imports the document readers.
